# Level 4 → 5

## 1. 목표 (Objective)
페이지 내에서 비밀번호 찾기

## 2. 사용 명령어 (Commands)
`없음`

## 3. 풀이 과정 (Procedure)
1. 페이지 내용은 접근 거부, 무조건 주어진 주소로부터 와야 한다는 내용이 존재
    Refresh page 버튼을 누르니 natas4로 접근했다는 내용이 존재
2. 정보가 쿠키에 담긴 것인지 궁금해 개발자도구를 열어 `Storage` 탭으로 이동
    - 별다른 내용이 없음
3. `Network` 탭으로 이동 후 무슨 데이터가 주고 받아지는지 확인
    - `Request Header`에 `Referer` 항목이 존재
4. Burp Suite를 통해 proxy 변조를 진행함
    - intercept on으로 변경 후 `Referer`를 지정된 주소로 변경

## 4. 원리 (Theory)
- `Header`
  - 클라이언트와 서버가 요청 또는 응답을 주고받을 때, 데이터 본문 외에 부가적인 정보를 담아 전달하는 역할
- `Referer`
  - 요청이 어느 페이지에서 왔는지(이전 페이지 URL)를 담는 요청 헤더
  - 클라이언트가 임의로 변조할 수 있어 인증·인가 수단으로 신뢰할 수 없음
- `Proxy`
  - 웹 클라이언트와 서버 사이에서 통신을 중계하여 요청과 응답을 대신 전달해주는 중간 서버
  - 중간 서버가 요청을 잠시 잡아 내용을 수정해서 보내는 것이 가능

# 보고서
> 워게임의 비밀번호가 노출된 것이 아닌, admin 계정이 노출된 것으로 산정
> 데이터 변경 기능이 확인되지 않아 무결성 영향은 낮게 산정

## 1. 취약점 요약
| 항목 | 내용 |
|------|------|
| 취약점명 | Referer 헤더 기반 접근 통제 우회 |
| 분류 | CWE-293 (Using Referer Field for Authentication) |
| 대상 | natas4 웹 페이지 |
| 위험도 | 8.2 (High) |
| 벡터 | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N` |

## 2. 취약점 설명
- 서버가 클라이언트가 보내는 `Referer` 헤더 값만으로 접근 허용 여부를 판단함
- `Referer`는 클라이언트가 임의로 변경할 수 있는 값이므로 프록시 도구로 허용된 주소로 조작하면 접근 통제를 우회할 수 있음

## 3. 재현 절차
1. 대상 페이지 접속 → 접근 거부 메시지 확인
2. 개발자도구 `Network` 탭에서 요청 헤더의 `Referer` 항목 확인
3. Burp Suite에서 intercept를 켜고 요청 캡처
4. `Referer` 값을 허용된 주소로 변경 후 전달 → 접근 허용 및 계정 정보 확인

## 4. 영향 (Impact)
- 접근 통제 우회로 admin 계정 정보가 노출되어 관리자 권한으로 접근 및 정보 열람 가능, 변경 기능은 확인되지 않아 무결성 영향은 낮게 산정
- 프록시 도구만 있으면 공격이 가능하며 별도의 고급 기법이 필요하지 않아 악용 난이도가 낮음

## 5. 대응 방안 (Remediation)
- `Referer` 등 클라이언트가 제어할 수 있는 헤더를 인증·인가 수단으로 사용하지 않기
- 서버 측 세션·토큰 기반 인증 및 권한 검사 적용
- `Referer`는 보조적인 CSRF 방어 용도로만 활용
